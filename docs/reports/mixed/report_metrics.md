# Оценка качества автоматически сгенерированных тестов

---

## 1. Цель эксперимента

Для сравнения различных инструментов автоматической генерации тестов необходимо использовать набор объективных метрик. Они позволяют количественно оценить полученные тестовые наборы и наглядно сравнить преимущества и недостатки различных подходов.

В рамках эксперимента будут рассматриваться следующие метрики:

1. Количество сгенерированных тестов
2. Время генерации тестов
3. Покрытие строк
4. Покрытие ветвей
5. Разнообразие входных данных
6. Mutation Score (оценка мутационного тестирования)
7. Способность находить реальные ошибки
8. Покрытие контракта (Contract Coverage)
9. Доля запускающихся без правки (Runnability)
10. Стоимость генерации (Generation Cost)

---

## 2. Описание метрик

### 2.1. Количество сгенерированных тестов (Test Suite Size)

Данная метрика показывает количество тестовых случаев (test cases), сгенерированных инструментом.При подсчёте учитываются именно отдельные тестовые случаи, а не количество выполняемых внутри них HTTP-запросов.

Само по себе большое количество тестов не означает высокое качество тестового набора. Поэтому данную метрику необходимо рассматривать в совокупности с другими показателями.

Она позволяет оценить:

- какой объём тестов генерирует инструмент;
- сколько тестов требуется для достижения определённого уровня покрытия или качества;
- какой инструмент способен достичь сопоставимого или более высокого качества при меньшем количестве тестов.

### 2.2. Время генерации тестов (Test Generation Time)

Метрика показывает, сколько времени инструменту требуется для создания тестового набора.

При проведении эксперимента важно разделять:

- **время генерации** — время, которое инструмент затрачивает на поиск и создание тестов;
- **время выполнения** — время, необходимое для запуска уже сгенерированных тестов.

Основной характеристикой для сравнения генераторов является время генерации. Время выполнения может рассматриваться дополнительно при оценке общей эффективности тестового набора.

### 2.3. Покрытие строк (Line Coverage)

Покрытие строк показывает, какая доля исполняемых строк исходного кода была выполнена хотя бы одним сгенерированным тестом.Метрика позволяет оценить, какую часть исходного кода затрагивает тестовый набор.Рассчитывается по формуле:

**Line Coverage = (количество выполненных строк / общее количество исполняемых строк) × 100%**

Высокое покрытие строк показывает, что тесты затрагивают большую часть программы. Однако оно не гарантирует, что соответствующие участки кода действительно проверяются. Строка может быть выполнена тестом, но результат её выполнения при этом может не проверяться.Поэтому покрытие строк также лучше рассматривать в совокупности с другими метриками качества тестового набора.

### 2.4. Покрытие ветвей (Branch Coverage)

Покрытие ветвей показывает, какая доля возможных вариантов выполнения программы была пройдена сгенерированными тестами.Ветви возникают, например, в условных конструкциях `if/else`, `switch` и других элементах управления потоком выполнения программы.Рассчитывается по формуле:

**Branch Coverage = (количество пройденных ветвей / общее количество ветвей) × 100%**

Покрытие ветвей является более информативным показателем по сравнению с простым покрытием строк, поскольку позволяет оценить, проверяют ли тесты различные варианты логики программы.При этом высокое покрытие ветвей также не гарантирует обнаружение ошибок. Тест может пройти определённую ветвь, но не содержать достаточных проверок результата её выполнения.

### 2.5. Разнообразие входных данных (Input Diversity)

Разнообразие входных данных показывает, насколько различаются входные значения, используемые сгенерированными тестами.Метрика позволяет оценить, насколько широко инструмент исследует возможные варианты входных данных, а не ограничивается небольшим количеством похожих сценариев.

При оценке могут учитываться различные характеристики входных данных:

- количество уникальных значений;
- диапазон используемых значений;
- наличие граничных значений;
- наличие корректных и некорректных значений;
- разнообразие комбинаций входных параметров.

Высокое разнообразие входных данных может способствовать обнаружению ошибок, которые возникают только при определённых значениях параметров или их комбинациях.

> **Способ измерения:** Для строковых параметров используется оценка энтропии Шеннона или индекс уникальности (количество уникальных значений / общее число запросов). Для числовых параметров — разброс (variance) и проверка наличия граничных значений (min/max из OpenAPI спецификации).

### 2.6. Mutation Score (оценка мутационного тестирования)

Mutation Score показывает, насколько хорошо тестовый набор способен обнаруживать небольшие изменения в исходном коде программы.Для проведения мутационного тестирования в исходный код автоматически вносятся небольшие изменения, называемые мутациями. После этого сгенерированные тесты запускаются для каждого мутанта. Если тесты обнаруживают изменение и завершаются с ошибкой, мутация устранена. Если тесты проходят успешно, мутация не замечена - соответственно это недочет инструмента.

Метрика рассчитывается по формуле:

**Mutation Score = (замеченные мутации / общее количество анализируемых мутаций) × 100%**

Данная метрика позволяет оценить не только то, выполняют ли тесты код, но и насколько эффективно они способны обнаруживать изменения в его поведении. Поэтому Mutation Score является одной из наиболее важных метрик для оценки качества автоматически сгенерированных тестов.

> **Примечание для API (Black-box):** Поскольку инструменты работают на уровне черного ящика, мутации вносятся на уровень API-контракта (например, смена типов данных в OpenAPI, удаление обязательных полей в ответе, изменение статус-кодов). Используются инструменты типа `Schemathesis` (stateful testing) или самописные скрипты-мутаторы OpenAPI-спецификации.

### 2.7. Способность находить реальные ошибки (Fault Detection Rate)

Данная метрика показывает, насколько эффективно сгенерированный тестовый набор обнаруживает заранее известные реальные дефекты в программе.Для её оценки используется набор дефектов, каждый из которых должен быть воспроизводимым и иметь известное ожидаемое поведение. Тестовый набор запускается на версиях программы, содержащих эти дефекты, после чего определяется количество обнаруженных ошибок.

Метрика рассчитывается по формуле:

**Fault Detection Rate = (количество обнаруженных дефектов / общее количество проверяемых дефектов) × 100%**

Данная метрика непосредственно показывает способность тестов обнаруживать реальные ошибки, поэтому является важным показателем их практической эффективности.Однако для её использования необходимо иметь набор заранее известных и воспроизводимых дефектов. Если такого набора нет, метрику нельзя корректно рассчитать.

### 2.8. Покрытие контракта (Contract Coverage)

Данная метрика показывает, какая доля элементов API-контракта (OpenAPI/Swagger) покрыта сгенерированными тестами. В отличие от покрытия строк кода, здесь оценивается покрытие именно спецификации API.

При расчёте учитываются следующие элементы контракта:

- **Endpoints:** какие пути API имеют хотя бы один тестовый запрос;
- **HTTP-методы:** какие операции (GET, POST, PUT, DELETE и т.д.) покрыты;
- **Статус-коды:** проверяются ли documented статусы ответов (200, 201, 400, 404, 500 и т.д.);
- **Схемы ответов:** проверяется ли структура JSON-ответа на соответствие схеме в контракте;
- **Параметры:** покрываются ли path/query/header параметры.

Рассчитывается по формуле:

**Contract Coverage = (покрытые элементы контракта / общее количество элементов в контракте) × 100%**

Данная метрика критична для проекта, поскольку основной вход — это API-контракт. Инструменты вроде Microcks (`OPEN_API_SCHEMA` runner) измеряют её напрямую через Conformance Score. Schemathesis проверяет статусы и Content-Type, но не в явном виде считает покрытие всех элементов контракта.

### 2.9. Доля запускающихся без правки (Runnability)

Данная метрика показывает, какой процент сгенерированных тестов выполняется без ручной доработки (исправления синтаксиса, подстановки импортов, исправления логики и т.д.).

Рассчитывается по формуле:

**Runnability = (количество тестов, запустившихся без правки / общее количество сгенерированных тестов) × 100%**

Это одна из ключевых метрик проекта, поскольку автоматическая генерация теряет смысл, если большинство тестов требует ручного исправления перед запуском.

**Ориентиры из обзора рынка:**

- Классические детерминированные инструменты (Schemathesis, EvoMaster): до **92%**запускаемости;
- LLM-подходы (APITestGenie): до **89%** после ≤3 попыток self-repair, но вариативно;
- Чистая LLM-генерация без пост-обработки: значительно ниже, часто требует ручной правки.

Для гибридного пайплайна (LLM + детерминированная пост-обработка) целевая метрика — максимизация Runnability за счёт автоматической фиксации синтаксиса и импортов без участия человека.

### 2.10. Стоимость генерации (Generation Cost)

Данная метрика измеряет полную стоимость создания тестового набора, включая вычислительные и финансовые затраты.

При расчёте учитываются:

- **Время генерации** (секунды) — сколько инструмент работал;
- **Число обращений к LLM** — для LLM-генераторов;
- **Токены** (prompt + completion) — расход токенов при использовании LLM;
- **Денежная стоимость** ($) — стоимость API-вызовов к LLM-провайдеру.

Рассчитывается по формуле:

**Cost_per_endpoint = (total_tokens × price_per_token + T_gen × compute_cost) / N_endpoints**

Данная метрика является **уникальной нишей проекта**. По результатам трёх независимых обзоров (GPT, Odysseus, DeepSeek) измерение стоимости генерации почти никем на рынке не реализовано. Например, QAAI заявляет ~$0.21 на 20 endpoints, но детального учёта токенов и времени нет.

Для нашего гибридного пайплайна важно измерять:

- сколько стоит генерация на эндпоинт;
- сколько стоит одна итерация self-repair;
- какой trade-off между стоимостью LLM и качеством детерминированной пост-обработки.
