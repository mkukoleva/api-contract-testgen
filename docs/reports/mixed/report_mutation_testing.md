# Результат задач 2.2.9 и 4.1.4

## Запуск

Команды выполняются из корня репозитория. Сначала установите зависимости
в `prototype` командой `uv sync --locked`, настройте доступ к LLM в
`prototype/.env` и подготовьте Docker и образ runner по инструкции
[prototype/ReadMe.md](../../../prototype/ReadMe.md).

Общая приёмка HTTP-генерации и мутаций (регрессия, две версии контрольного API,
user story, внесённые дефекты и Catalogue-кампания):

```bash
DEEPCODE_MAX_OUTPUT_TOKENS=16000 PYTHONDONTWRITEBYTECODE=1 prototype/.venv/bin/python tools/accept_tasks.py
```

Отдельная приёмка unit-генерации:

```bash
DEEPCODE_MAX_OUTPUT_TOKENS=16000 PYTHONDONTWRITEBYTECODE=1 prototype/.venv/bin/python tools/accept_unit.py
```

Запускайте команды последовательно. Они используют реальную LLM и Docker.
16000 — настраиваемый предел ответа модели, а не требование ТЗ; на 8000
большой ответ с кодом может обрезаться. Значение действует только на запуск.
Отчёты сохраняются в `.acceptance-runs/` и `.unit-generation-runs/`;
генерируемые тесты вручную не исправляются.

Регрессия без новой LLM-генерации:

```bash
PYTHONDONTWRITEBYTECODE=1 prototype/.venv/bin/python tools/verify.py
```

## Как устроена проверка мутаций

По исходному контракту создаются три вида изменений наблюдаемого ответа:
подмена типа значения, удаление обязательного поля и подмена HTTP-статуса.
Например, `price: 100` заменяется на строку, из JSON удаляется `name` или
статус 200 заменяется на 500. Один прогон применяет один план мутации;
тестовый набор, исходный контракт и проверки во время измерения неизменны.
Изменение файла спецификации само по себе не считается поведенческой мутацией.

Для результата `killed` требуются успешный baseline, подтверждённая доставка
дефектного ответа тесту, два воспроизводимых обнаружения и успешное
восстановление на исходном ответе. Успешный полный прогон с доставленной
мутацией означает `survived`. Недоставленные, недопустимые, неподдерживаемые
и неопределённые случаи показываются отдельно с причиной; ошибки окружения
не засчитываются как обнаружение. Независимая проверка нарушения контракта
подтверждает применимость плана, но не заменяет проверку оцениваемых тестов.

Mutation Score = `100 × killed / (killed + survived)`.
Доля оценённых применимых целей =
`100 × (killed + survived) / (killed + survived + not_exercised + inconclusive)`.
При нулевом знаменателе или неуспешном baseline результат не рассчитывается.
`invalid` и `unsupported` не включаются в знаменатели, но остаются в отчёте.
100% в актуальном прогоне относится к 46 response-мутациям выбранного
Catalogue-контракта и нового набора тестов, а не ко всем возможным дефектам.

Поддерживаемая область исполняемых планов: OpenAPI 3.0.x, JSON-ответы и
локальные `$ref`. Внешние и рекурсивные ссылки, композиции схем отмечаются
как неподдерживаемые. Catalogue использует Swagger-адаптер. При сравнении
наборов важны одинаковые контракт, планы мутаций и образ runner.

## HTTP-генерация и обнаруженный пробел

Генератор строит normal, boundary и error тесты, использует доверенные HTTP-
фикстуры и может связать операции в user story. Он сохраняет версии набора,
хеш контракта, модель и время запуска. Недостаток применимых категорий даёт
`incomplete_categories`; неполнота исходного контракта обозначается
`needs_contract_clarification`.

Повтор пользователя обнаружил, что массив одновременно нарушал `maxItems`
и `enum`. Такой запрос не доказывает отдельную проверку границы длины.
Конвейер теперь сохраняет наблюдения JSON-запросов, отмечает непокрытые
входные условия и ограниченно добавляет новые файлы тестов; уже проходивший
набор защищён от замены. При оставшихся пробелах статус — `incomplete_inputs`.
Отдельный случай с пустым raw-телом (`data=""`) исправлен узкой обработкой
явно помеченных примеров повреждённого JSON; вход становится непустым `{`,
ожидаемый статус и проверки ответа не ослабляются. Область этого механизма
ограничена пустыми raw-примерами с явной положительной пометкой malformed JSON;
missing-body, отрицания этой пометки и невызванные helper не используются
для такой нормализации.
