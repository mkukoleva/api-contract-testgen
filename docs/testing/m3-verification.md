# Проверка M3 по ТЗ ARQA v3

Основание: раздел 7.10, пп. 4.1.7.1, 4.5.2.2–4.5.2.3, общий лимит
сбора и выполнения из п. 4.1.10. Этот документ описывает проверки M3;
он не заменяет полную программу и методику приёмочных испытаний из п. 5.1.

## Границы

M3 получает готовый pytest-код, запускает его в изоляции и при конкретной
ошибке кода ограниченно исправляет и повторно проверяет набор. Генерация
качественных сценариев относится к M2. Связь с основным агентом и CLI проверяется
в режиме `--generate`; это не означает завершения остальных требований M2/M5.
Метрики не изменяются.

Синтаксис проверяется на хосте через AST без импорта. Сбор и исполнение
выполняются только в Docker. Сетевая политика настраивается до импорта тестов;
worker лишён прав менять её. Разрешён один TCP-адрес и порт тестируемого API.
Интернет, хост, база, посторонние контейнеры, внешний DNS, UDP и IPv6 блокируются.
Проверяются также дочерние процессы, редиректы и невозможность снять ограничения.
Локальный loopback контейнера используется для доверенных инфраструктурных проверок.

Адрес, сети, output-каталоги, timeout и лимиты ремонта задаёт доверенный Python-
оркестратор через GenerationSettings. Основной агент в режиме `--generate`
использует create_generation_tool(settings): этот инструмент принимает только
пустой объект аргументов и отклоняет попытки передать настройки от LLM.
Старый generate_tests_tool оставлен для совместимости доверенных Python-вызовов;
его свободные параметры нельзя регистрировать как LLM-интерфейс.

## Самокоррекция

Кандидат ремонта применяется только после структурной проверки:

- пропущенное двоеточие в заголовке функции/класса восстанавливается обычным
  кодом для построения опорного AST; кандидат должен сохранить остальной код;
- допускаются отсутствующие import pytest/import requests и известные опечатки
  pytes as pytest/request as requests; новые импорты не могут затенять привязки.
  Порядок существующих импортов, docstring и future-директив сохраняется;
- диагностированная отсутствующая фикстура client/http_client/session может
  стать api_client, baseurl/api_url — base_url. Имя аргумента и его использования
  заменяются согласованно. Коллизии и неоднозначные вложенные области отклоняются;
- assert, данные запроса, URL, HTTP-методы, декораторы, управление выполнением
  и остальные тесты сохраняются. Неоднозначный синтаксис и неизвестные импорты
  требуют проверки; произвольный переписанный модуль автоматически не принимается.

Падение проверки API само по себе, включая документированный альтернативный
статус, не вызывает ремонт. Ошибка подключения к API при импорте или исполнении,
infrastructure_error, timeout и interrupted также не вызывают ремонт.
Это классификация наблюдений, а не доказательство, что любое падение assert
обязательно является дефектом сервиса.

По умолчанию разрешены три вызова ремонта; TESTGEN_MAX_REPAIR_ATTEMPTS задаёт
число попыток, TESTGEN_REPAIR_TOKEN_BUDGET — бюджет выходных токенов (по умолчанию
30000). Бюджет проверяется перед следующим вызовом и может быть превышен последним
ответом; это не жёсткий лимит расхода провайдера. Одинаковая ошибка после ремонта
останавливает цикл. Исходный код и каждый принятый кандидат сохраняются версиями.
`--max-repair-attempts 0` отключает ремонт; обрезанный ответ модели не применяется.
Повторный запуск сохранённого набора через runner не обращается к LLM.

## Запуск проверок

Из корня проекта в PowerShell, после установки зависимостей:

```powershell
docker build -t api-contract-pytest-runner:step5 prototype/src/prototype/service_tools/runner
py -3.12 -m uv run --project prototype --locked --no-sync python tools/verify.py --report-root "$env:TEMP/api-contract-verification"
```

Полный verify поднимает/проверяет Catalogue, запускает тесты M3 и сохранённые
наборы, сохраняет доказательства вне репозитория. Реальные запросы к LLM отсутствуют.
Существующий стенд сохраняется; временные контейнеры runner удаляются.

Для отдельной проверки M3 на готовом стенде:

```powershell
$env:RUN_RUNNER_CATALOGUE_TESTS = '1'
$m3Files = @(Get-ChildItem prototype/src/prototype/tests/test_m3_*.py | ForEach-Object { $_.FullName })
py -3.12 -m uv run --project prototype --locked --no-sync python -m pytest @m3Files -q
```

Полный `verify` собирает эти тесты автоматически.

## Демонстрация с настоящей моделью

Текущая модель API — Qwen3.8-Flash-Next. Точный идентификатор модели из API
задаётся через `DEEPCODE_MODEL` в окружении или `prototype/.env`; ключ и URL
подключения — через `DEEPCODE_API_KEY` и `DEEPCODE_BASE_URL`. Названия переменных
сохранены для совместимости. Демо использует локальный Catalogue; серверные
стенды для этой проверки не требуются. В каталоге `prototype`, после настройки
LLM, сборки runner и готовности стенда:

```powershell
py -3.12 -m uv run --locked tester ../benchmark/catalogue/catalogue.swagger.json --generate --base-url http://catalogue:8080 --network pytest-runner-catalogue_runner --blocked-network pytest-runner-catalogue_database --report-dir "$env:TEMP/api-contract-m3-reports" --tests-output-dir "$env:TEMP/api-contract-m3-tests"
```

Эта команда обращается к LLM. `verify` выше этого не делает: ответы модели
заданы тестами, но агент LangChain, storage, Docker, API и отчёты настоящие.
Сохранённый набор повторно запускается через `prototype.service_tools.runner`
без генератора и без вызовов модели. Отчёты каждой попытки содержат JSON,
Markdown и JUnit XML; ошибка жизненного цикла добавляет служебный testcase
`runner` в XML, не меняя результаты и знаменатель метрик.

## Критерии

| Проверка | Ожидаемый результат |
|---|---|
| Синтаксис → импорт → фикстура | ScriptedModel выдаёт исходный модуль и три кандидата; реальные storage/runner/API дают успех, четыре версии и три записи ремонта |
| Падение assert на живом API | failed сохраняется; дополнительного запроса к модели и изменения assert нет |
| Нет Docker/API, timeout, interrupted | Понятный статус и диагностика, нет ремонта, частичные результаты не превращаются в passed |
| Вредоносный кандидат | Изменение/обход assert, добавление skip, затенение имени или изменение сценария отклоняется до исполнения |
| Настройки от LLM | Bound-tool отклоняет адрес, сеть и лимиты до вызова конвейера |
| Изоляция | test_runner_isolation.py и политика контейнера проходят, включая импорт и дочерний процесс |
| Повтор ошибки и лимиты | Цикл останавливается по конфигурации; предыдущие версии и диагностика сохраняются |
| Агент → tool → конвейер → агент | Настоящий граф LangChain получает результат живого прогона; основной CLI сохраняет отчёт и возвращает код по фактическому статусу |
| Сохранённый набор → Python/CLI runner | Оба повторных прогона выполняют тот же код без вызовов модели; ключ из окружения хоста в контейнер не передаётся |
| Ошибки contract/model/storage/reports | Диагностика сохраняется, где доступен output; сбой сохранения не становится общим успехом, факты pytest не теряются |
| Дубли имён/отклонённые файлы | Дубли отклоняются до перезаписи; частично потерянный набор не даёт общий статус success |
| Ненулевой код pytest при прошедших тестах | completed_with_failures; основной CLI возвращает ненулевой код, дополнительного ремонта нет |
| Только skipped | completed_without_execution; пропуски сохраняются и не считаются успешным выполнением набора |
| Повторный/параллельный вызов bound-tool | Один запуск конвейера; повторы возвращают те же факты, CLI не дублирует результат |
| Ошибки входа и записи диагностики | Понятный код 2; input-error.json/Markdown, где доступен output; ошибка записи не скрывает исходную ошибку |
| Сложные пути и коды ответов | Параметры внутри сегмента не зависают; приоритет ответа: точный код, диапазон, default |
| Microcks connect/read/poll timeout | timeout; уже полученный ответ сохраняется как partial/raw, без выдуманного результата |
| Ошибка финального ответа агента | Уже полученный ToolMessage и отчёты M3 сохраняются; весь CLI завершается ненулевым кодом |
| Воспроизводимость | Метаданные контракта, модели и промптов совпадают в отчёте генерации и сохранённых версиях; CLI сохраняет run-metadata.json |

ScriptedModel — заранее заданные ответы вместо платного провайдера. Эти испытания
подтверждают M3, но не качество настоящей генерации M2 и не достижение метрик M4.

Последняя повторная проверка 2026-10-14 после исправлений аудита 4.1.1 и 4.1.7:
полный `verify` — 753 passed, без ошибок и пропусков; сохранённые наборы runner —
3 и 5 passed. Добавлено 88 проверок по сравнению с предыдущим набором из 665.
Изменения выполняются на стороне оркестратора, пересборка образа не потребовалась;
существующий стенд сохранён. LLM не вызывался, доказательства находятся в заданном внешнем
каталоге `--report-root`. Исторические результаты в README не подменяют эту проверку.
