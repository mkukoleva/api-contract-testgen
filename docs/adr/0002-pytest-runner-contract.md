# ADR 0002 — Интерфейс pytest-runner

Статус: реализован контракт данных, offline Docker-runner (этап 3),
сетевая изоляция до одного адреса API (этап 4) и автоматическая проверка
совместимости pytest: host-precheck синтаксиса без исполнения кода и фаза
`pytest --collect-only` внутри изоляции перед запуском (этап 5).
Подключение к модулям команды — следующие этапы.

## Границы изменения

Пункт 2.2.6 ТЗ требует pytest-совместимости и изолированного выполнения.
Первый этап определил вход и выход runner. Этап 3 добавил запуск в отдельном
контейнере без сети. Этап 4 добавил сетевую политику runner: доступ только
к адресу и порту сервиса, без интернета, хоста, базы данных и посторонних
контейнеров.
Текущий CLI `tester`, генерация user story и Schemathesis сохраняют
свой прежний сценарий работы. Новые структуры пока не подключены к агенту.

Модуль `prototype.service_tools.runner.contracts` использует только стандартную библиотеку.
Его импорт не загружает LLM, `.env`, YAML или инструменты агента. Создание
структур не выполняет запросов, не запускает процессы и не создаёт файлы.

## Ответственность участников

- Генератор сохраняет pytest-код, постобработка исправляет его до запуска.
- Доверенный CLI/оркестратор создаёт `RunConfig`. LLM и тестовый код не выбирают
  разрешённые адреса, лимит времени, команды Docker или параметры pytest.
- Runner принимает `RunConfig` и возвращает `RunResult`, выполняя сбор
  и тесты внутри уже настроенной изоляции.
- Self-repair получает конкретные ошибки тестового кода; недоступность стенда
  или падение проверки API сами по себе не являются поводом менять тест.
- Модуль оценки получает фактические результаты и сведения генератора об
  ожидаемом наборе. Runner не вызывает LLM и не рассчитывает стоимость генерации.

## Вход: RunConfig

| Поле | Тип | Значение |
|---|---|---|
| `tests_dir` | `Path` или `str` | Каталог подготовленных тестов |
| `output_dir` | `Path` или `str` | Каталог артефактов прогона |
| `base_url` | `str` или `None` | HTTP(S)-адрес сервиса; `None` означает режим без сети |
| `timeout_seconds` | число, по умолчанию `60.0` | Положительный конечный общий лимит сбора и выполнения |

Пути преобразуются в `Path` без обращения к файловой системе. Относительные
пути относятся к рабочему каталогу вызывающего процесса; runner разрешает
и проверяет их перед созданием контейнера. Проверка существования,
прав доступа и безопасного монтирования принадлежит runner.

URL может содержать префикс пути (`http://catalogue:80/api`). Запрещены учётные
данные в URL, query, fragment, пробелы и некорректный порт. Без явного порта
используются стандартные 80/443 для HTTP/HTTPS. Синтаксическая проверка URL
**не является сетевой защитой**: разрешение имени, фиксацию целевого адреса и
блокировку остальных соединений реализует изолированный запускатель.

Генератор передаёт обычные `test_*.py` с функциями `test_*`; параметры pytest,
зависимости и доверенные фикстуры предоставляет среда выполнения. Для
интеграции фиксируются имена фикстур `base_url` (строка) и `api_client`
(`requests.Session` с HTTP-таймаутом, отключённым наследованием proxy из среды
и контролем редиректов). С этапа 4 они предоставляются модулем
`runner_fixtures`, который копируется в образ и регистрируется worker как
плагин pytest. Unit-тесты могут обходиться без этих фикстур.
Сгенерированный код не должен определять собственную сетевую политику или
рассчитывать на ключи провайдера LLM.

## Выход: RunResult

| Статус | Значение |
|---|---|
| `completed` | Прогон завершён, отдельные тесты могли упасть |
| `collection_error` | pytest не смог корректно собрать набор |
| `infrastructure_error` | Не удалось подготовить или запустить окружение |
| `timeout` | Превышен лимит времени; допускаются частичные результаты |
| `no_tests` | Тесты не найдены; это не успешная проверка API |
| `interrupted` | Запуск прерван до завершения |

`exit_code` — фактический код pytest; `None`, если код не получен. Коды Docker
не подменяют коды pytest: сбой Docker описывается как `infrastructure_error`
с диагностикой в `error_message`. Ошибки сбора хранятся в `collection_errors`.
Поля `duration_seconds` всегда конечные и неотрицательные.

`tests` содержит один `TestResult` на полный pytest `nodeid`, включая суффикс
параметризации. `outcome`: `passed`, `failed`, `error`, `skipped`.
`phase`: `setup`, `call`, `teardown`. Ошибка setup/teardown имеет приоритет над
результатом тела теста; дополнительные детали фаз сохраняются в `message`.
Повторные попытки self-repair оформляются отдельными прогонами.

`to_dict()` выдаёт JSON-совместимые данные, включая вычисленную сводку `summary`.
Ошибки сбора считаются отдельно от результатов отдельных тестов.
`compatibility_issues` — структурированные проблемы pytest-совместимости
(`category`: `syntax`/`import`/`collection`, `path`, `line`, `column`,
`message`, `auto_fixable`) для передачи в модуль постобработки; найденные
host-precheck синтаксические ошибки дополнительно дублируются
в `collection_errors` форматом `path:line:column: message`.
`report_paths` связывает названия артефактов с путями, например `junit`
и `json`; с этапа 5 доступны также `precheck` и `collect_events`.
Сериализация ничего не сохраняет; полноценные отчёты относятся к этапу 6.

## Реализация этапа 3

На этапе 3 `prototype.service_tools.runner.docker_runner.run_tests(config)`
использовал заранее собранный образ `api-contract-pytest-runner:step3` и
поддерживал только `base_url=None`. Отдельный CLI доступен через
`python -m prototype.service_tools.runner`; прежний `tester` не изменён.
На этапе 4 `run_tests` принимает также `network`/`blocked_networks`, а образ
собран как `api-contract-pytest-runner:step4`. На этапе 3 контейнер создавался
с `--network none`
до импорта тестов, без capabilities, с непривилегированным пользователем,
read-only корневой ФС, лимитами памяти/процессов и временным `/tmp`.
Каталог тестов монтируется read-only, отдельный новый каталог диагностики —
на запись. `.env`, ключи LLM и Docker socket внутрь не передаются. Образ включает
только Python, pytest с зависимостями и worker. Сборка образа выполняется явно;
runner не устанавливает зависимости и не скачивает образы.

Worker получает события pytest через hooks, записывает и сбрасывает JSONL после
каждой фазы. Host-runner объединяет setup/call/teardown в один `TestResult`.
Ошибки сбора не становятся тестовыми случаями. При аварийном выходе отсутствие
события завершения pytest считается ошибкой окружения, даже если контейнер
завершился с кодом 0. При таймауте учитываются только законченные тесты.

Доверенный launcher ограничивает время создания контейнера, сбора и выполнения.
В `finally` удаляется только созданный им контейнер с уникальным именем;
`docker rm --force` завершает и дочерние процессы. Очистке отведено дополнительно
до 10 секунд. Ошибка очистки возвращается с именем оставшегося контейнера.
События и логи остаются для диагностики; это вывод тестового процесса,
а не защищённое от подделки доказательство корректности произвольного кода.

Ограничения этапа 3: нет доступа к Catalogue, HTTP-фикстур, отдельной предварительной
проверки синтаксиса, полной проверки сетевых обходов, self-repair или метрик.
Сетевая изоляция сервиса реализована на этапе 4.

`failed` при проверке ответа API не означает, что тест не запускается.
`skipped` не доказывает выполнение тела теста. Из `passed / total` нельзя
вычислять Runnability. Для этой метрики нужны исходный перечень тестовых случаев
от генератора и согласованная классификация ошибок. При неполном сборе и
неизвестном исходном количестве процент не рассчитывается.

## Реализация этапа 4 — сетевой доступ только к API

`run_tests(config, *, image=..., network=None, blocked_networks=())`:

- `base_url=Catalogue` и `--network` включают service mode: контейнер подключается
  только к internal-сети runner стенда (`pytest-runner-catalogue_runner`),
  в которой находится ровно один контейнер — Catalogue. База (`catalogue-db`)
  привязана к сети `database`; runner к ней не подключён.
- Preflight: `docker network inspect` сети runner подтверждает ровно один
  контейнер и возвращает его IPv4 и IPv4 gateway. Имя из `base_url`
  (например `http://catalogue:8080`) фиксируется в `/etc/hosts` через
  `--add-host <имя>:<IPv4>`; базовый URL должен быть обычным именем, не IP
  и не содержать символов, опасных для формата hosts.
- `--blocked-network` (повторяемый) добавляет в переменную окружения
  `RUNNER_UNREACHABLE` IPv4-адреса всех контейнеров сети (например сети
  `database`); туда же попадает gateway сети runner. Port-фильтрация портов
  на уровне Docker не используется: сеть runner не даёт доступа к этим
  адресам, а policy-набор перепроверяет это внутри контейнера.
- В образ передаются переменные `RUNNER_BASE_URL`, `RUNNER_API_IP`,
  `RUNNER_GATEWAY_IP`, `RUNNER_UNREACHABLE` (CSV), `RUNNER_TIMEOUT_SECONDS`.
- Worker сначала исполняет доверенный policy-набор
  `/opt/runner/policy_tests/test_network_policy.py` и пишет результаты в
  отдельный `policy_events.jsonl`. Этот набор использует те же фикстуры
  `base_url`/`api_client`, что и сгенерированные тесты, и проверяет:
  health Catalogue; соответствие DNS pinned-IP; недоступность интернета
  (53/443), gateway/host, базы и адресов `RUNNER_UNREACHABLE`; недоступность
  внешнего DNS и IPv6; запрет raw-socket; наследование ограничений дочерними
  процессами; отказ client следовать редиректам (в т.ч. на внешний хост
  через локальный сервер-редиректер) и отсутствие proxy-переменных.
- Если policy-набор не подтвердил изоляцию (любой `skipped`/`failed`/`error`,
  ошибка сбора, отсутствие события завершения или завершение с ненулевым
  кодом), сгенерированные тесты **не запускаются вовсе**: worker дописывает в
  policy-события маркер `policy_blocked` и завершается кодом прогона policy.
  Host-runner видит непройденный policy-набор и возвращает
  `infrastructure_error`, в том числе когда прогон был прерван по таймауту.
  Обнаруженный обход сети останавливает прогон; бессмысленно продолжать с
  недостоверными данными.
- Offline-режим (`base_url=None`) не изменился: `--network none`, policy-набор
  не исполняется, HTTP-фикстуры в offline недоступны (требуют
  `RUNNER_BASE_URL`).
- Контейнер по-прежнему создаётся `docker create` + `docker start --attach`
  под каждый прогон; это не постоянный HTTP-сервис. Образ пересобран как
  `api-contract-pytest-runner:step4` и включает `requests` (и его зависимости).

Остаётся ограничение: policy-тесты и сгенерированные тесты исполняются в
одной изоляции, поэтому корректность изоляции перепроверяется только до
начала пользовательских тестов. `docker network inspect` — источник
"единственного контейнера"; наличие других контейнеров в сети runner
рассматривается как ошибка окружения.

## Реализация этапа 5 — автоматическая проверка совместимости pytest

Конвейер проверки совместимости из трёх стадий:

1. **Host-precheck без исполнения кода** (`compat.py`, только стандартная
   библиотека). `precheck_syntax(tests_dir)` — это `ast.parse` каждого
   `*.py` в каталоге тестов (включая `conftest.py` и helper-модули). Код
   не импортируется и не выполняется; контейнер при ошибках не создаётся.
   Это **жёсткий барьер**: синтаксическая ошибка возвращает
   `collection_error` с точной `path:line:column`, набором
   `compatibility_issues` и артефактом `precheck.json`. Проблемы с однозначно
   очевидным исправлением (`unexpected EOF`, незакрытая строка/скобка и т.п.)
   помечаются `auto_fixable=True` — это структурированный вход модуля
   постобработки; сам модуль и применение фиксов — следующий этап.
2. **Сбор в изоляции**. Worker сначала запускает `pytest --collect-only`
   внутри того же контейнера и той же сетевой политики: сбор импортирует
   Python-модули, поэтому он не может выполняться на хосте. Ошибки импорта
   и сбора фиксируются в `collect_events.jsonl` до запуска тестов.
3. **Запуск**. Тела тестов выполняются только после успешного сбора.

Порядок в service-режиме: policy-набор → collect-only → запуск; сбой policy
не допускает даже сбора. Offline-режим: collect-only → запуск. Worker
принимает формы `TESTS_DIR EVENTS COLLECT_EVENTS` (offline) и
`POLICY_DIR TESTS_DIR POLICY_EVENTS EVENTS COLLECT_EVENTS` (service);
двухаргументных форм этапа 3/4 больше нет. Host-runner читает фазу сбора
через `read_collection`: ошибки сбора → `collection_error`, отсутствие
завершения сбора → `infrastructure_error`, нулевой набор → `no_tests`.
Импорт-сайд-эффекты (сеть, файлы, `os._exit` во время импорта) перехватываются
фазой сбора в изоляции, и ни одно тело теста не выполняется. Образ пересобран
как `api-contract-pytest-runner:step5` (изменён только `pytest_worker.py`).

## Пример обмена

```python
import json
from prototype.service_tools.runner.contracts import RunConfig, RunResult, TestResult

config = RunConfig(
    tests_dir="generated/run-001",
    output_dir="reports/run-001",
    base_url="http://catalogue:80",
    timeout_seconds=60,
)

# Пример результата будущего runner, а не фактический запуск тестов.
result = RunResult(
    status="completed",
    exit_code=1,
    duration_seconds=0.4,
    tests=(TestResult(
        nodeid="test_catalogue.py::test_missing_product",
        outcome="failed",
        message="Ожидался документированный ответ, получен HTTP 500",
    ),),
)
payload = json.dumps(result.to_dict(), ensure_ascii=False, allow_nan=False)
```

## Совместимость и проверка

Сигнатуры `main()`, `run(contract_path)` и `build_agent()` сохранены. Зависимости
агента импортируются при создании агента; парсер — при запуске `run()`.
Системный промпт и четыре инструмента не изменены. Для новых потребителей
публичный путь импорта структур — `prototype.service_tools.runner.contracts`.

В установленном окружении проекта, из каталога `prototype`:

```bash
uv run --locked python -m pytest src/prototype/tests -q
```

Проверки контракта не используют Docker, сеть или LLM. Тест сборки агента
подменяет внешние зависимости и проверяет передачу прежней модели, промпта и
инструментов; он не заменяет сквозной прогон с настоящим провайдером.

Проверка этапа 1 от 2026-09-22: Python 3.14.7, pytest 9.1.1,
38 тестов прошли (37 новых проверок и существующий smoke-тест).
Инструкции для PowerShell и настройки PyCharm находятся в
[README прототипа](../../prototype/ReadMe.md).
