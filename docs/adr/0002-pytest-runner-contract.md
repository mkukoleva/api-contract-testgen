# ADR 0002 — Интерфейс pytest-runner

Статус: реализован контракт данных и минимальный offline Docker-runner (этап 3).
Сетевая политика для API и подключение к модулям команды — следующие этапы.

## Границы изменения

Пункт 2.2.6 ТЗ требует pytest-совместимости и изолированного выполнения.
Первый этап определил вход и выход runner. Этап 3 добавил запуск в отдельном
контейнере без сети; доступ только к API сервиса будет реализован на этапе 4.
Текущий CLI `tester`, генерация user story и Schemathesis сохраняют
свой прежний сценарий работы. Новые структуры пока не подключены к агенту.

Модуль `prototype.runner.contracts` использует только стандартную библиотеку.
Его импорт не загружает LLM, `.env`, YAML или инструменты агента. Создание
структур не выполняет запросов, не запускает процессы и не создаёт файлы.

## Ответственность участников

- Генератор сохраняет pytest-код, постобработка исправляет его до запуска.
- Доверенный CLI/оркестратор создаёт `RunConfig`. LLM и тестовый код не выбирают
  разрешённые адреса, лимит времени, команды Docker или параметры pytest.
- Runner принимает `RunConfig` и возвращает `RunResult`, выполняя сбор
  и тесты внутри уже настроенной изоляции.
- Self-repair получает конкретные ошибки тестового кода; недоступность стенда
  или падение проверки API сами по себе не являются поводом менять тест.
- Модуль оценки получает фактические результаты и сведения генератора об
  ожидаемом наборе. Runner не вызывает LLM и не рассчитывает стоимость генерации.

## Вход: RunConfig

| Поле | Тип | Значение |
|---|---|---|
| `tests_dir` | `Path` или `str` | Каталог подготовленных тестов |
| `output_dir` | `Path` или `str` | Каталог артефактов прогона |
| `base_url` | `str` или `None` | HTTP(S)-адрес сервиса; `None` означает режим без сети |
| `timeout_seconds` | число, по умолчанию `60.0` | Положительный конечный общий лимит сбора и выполнения |

Пути преобразуются в `Path` без обращения к файловой системе. Относительные
пути относятся к рабочему каталогу вызывающего процесса; runner разрешает
и проверяет их перед созданием контейнера. Проверка существования,
прав доступа и безопасного монтирования принадлежит runner.

URL может содержать префикс пути (`http://catalogue:80/api`). Запрещены учётные
данные в URL, query, fragment, пробелы и некорректный порт. Без явного порта
используются стандартные 80/443 для HTTP/HTTPS. Синтаксическая проверка URL
**не является сетевой защитой**: разрешение имени, фиксацию целевого адреса и
блокировку остальных соединений реализует изолированный запускатель.

Генератор передаёт обычные `test_*.py` с функциями `test_*`; параметры pytest,
зависимости и доверенные фикстуры предоставляет среда выполнения. Для будущей
интеграции фиксируются имена фикстур `base_url` (строка) и `api_client`
(`requests.Session` с HTTP-таймаутом, отключённым наследованием proxy из среды
и контролем редиректов). Они ещё не реализованы. Unit-тесты могут обходиться
без этих фикстур. Сгенерированный код не должен определять собственную сетевую
политику или рассчитывать на ключи провайдера LLM.

## Выход: RunResult

| Статус | Значение |
|---|---|
| `completed` | Прогон завершён, отдельные тесты могли упасть |
| `collection_error` | pytest не смог корректно собрать набор |
| `infrastructure_error` | Не удалось подготовить или запустить окружение |
| `timeout` | Превышен лимит времени; допускаются частичные результаты |
| `no_tests` | Тесты не найдены; это не успешная проверка API |
| `interrupted` | Запуск прерван до завершения |

`exit_code` — фактический код pytest; `None`, если код не получен. Коды Docker
не подменяют коды pytest: сбой Docker описывается как `infrastructure_error`
с диагностикой в `error_message`. Ошибки сбора хранятся в `collection_errors`.
Поля `duration_seconds` всегда конечные и неотрицательные.

`tests` содержит один `TestResult` на полный pytest `nodeid`, включая суффикс
параметризации. `outcome`: `passed`, `failed`, `error`, `skipped`.
`phase`: `setup`, `call`, `teardown`. Ошибка setup/teardown имеет приоритет над
результатом тела теста; дополнительные детали фаз сохраняются в `message`.
Повторные попытки self-repair оформляются отдельными прогонами.

`to_dict()` выдаёт JSON-совместимые данные, включая вычисленную сводку `summary`.
Ошибки сбора считаются отдельно от результатов отдельных тестов.
`report_paths` связывает названия артефактов с путями, например `junit` и `json`.
Сериализация ничего не сохраняет; полноценные отчёты относятся к этапу 6.
На этапе 3 `report_paths` содержит диагностические артефакты `log` и `events`.

## Реализация этапа 3

`prototype.runner.docker_runner.run_tests(config)` использует заранее собранный
образ `api-contract-pytest-runner:step3`. Отдельный CLI доступен через
`python -m prototype.runner`; прежний `tester` не изменён.

Поддерживается только `base_url=None`. Контейнер создаётся с `--network none`
до импорта тестов, без capabilities, с непривилегированным пользователем,
read-only корневой ФС, лимитами памяти/процессов и временным `/tmp`.
Каталог тестов монтируется read-only, отдельный новый каталог диагностики —
на запись. `.env`, ключи LLM и Docker socket внутрь не передаются. Образ включает
только Python, pytest с зависимостями и worker. Сборка образа выполняется явно;
runner не устанавливает зависимости и не скачивает образы.

Worker получает события pytest через hooks, записывает и сбрасывает JSONL после
каждой фазы. Host-runner объединяет setup/call/teardown в один `TestResult`.
Ошибки сбора не становятся тестовыми случаями. При аварийном выходе отсутствие
события завершения pytest считается ошибкой окружения, даже если контейнер
завершился с кодом 0. При таймауте учитываются только законченные тесты.

Доверенный launcher ограничивает время создания контейнера, сбора и выполнения.
В `finally` удаляется только созданный им контейнер с уникальным именем;
`docker rm --force` завершает и дочерние процессы. Очистке отведено дополнительно
до 10 секунд. Ошибка очистки возвращается с именем оставшегося контейнера.
События и логи остаются для диагностики; это вывод тестового процесса,
а не защищённое от подделки доказательство корректности произвольного кода.

Ограничения этапа: нет доступа к Catalogue, HTTP-фикстур, отдельной предварительной
проверки синтаксиса, полной проверки сетевых обходов, self-repair или метрик.
Они остаются в следующих пунктах плана.

`failed` при проверке ответа API не означает, что тест не запускается.
`skipped` не доказывает выполнение тела теста. Из `passed / total` нельзя
вычислять Runnability. Для этой метрики нужны исходный перечень тестовых случаев
от генератора и согласованная классификация ошибок. При неполном сборе и
неизвестном исходном количестве процент не рассчитывается.

## Пример обмена

```python
import json
from prototype.runner.contracts import RunConfig, RunResult, TestResult

config = RunConfig(
    tests_dir="generated/run-001",
    output_dir="reports/run-001",
    base_url="http://catalogue:80",
    timeout_seconds=60,
)

# Пример результата будущего runner, а не фактический запуск тестов.
result = RunResult(
    status="completed",
    exit_code=1,
    duration_seconds=0.4,
    tests=(TestResult(
        nodeid="test_catalogue.py::test_missing_product",
        outcome="failed",
        message="Ожидался документированный ответ, получен HTTP 500",
    ),),
)
payload = json.dumps(result.to_dict(), ensure_ascii=False, allow_nan=False)
```

## Совместимость и проверка

Сигнатуры `main()`, `run(contract_path)` и `build_agent()` сохранены. Зависимости
агента импортируются при создании агента; парсер — при запуске `run()`.
Системный промпт и четыре инструмента не изменены. Для новых потребителей
публичный путь импорта структур — `prototype.runner.contracts`.

В установленном окружении проекта, из каталога `prototype`:

```bash
uv run --locked python -m pytest src/prototype/tests -q
```

Проверки контракта не используют Docker, сеть или LLM. Тест сборки агента
подменяет внешние зависимости и проверяет передачу прежней модели, промпта и
инструментов; он не заменяет сквозной прогон с настоящим провайдером.

Проверка этапа 1 от 2026-09-22: Python 3.14.7, pytest 9.1.1,
38 тестов прошли (37 новых проверок и существующий smoke-тест).
Инструкции для PowerShell и настройки PyCharm находятся в
[README прототипа](../../prototype/ReadMe.md).
