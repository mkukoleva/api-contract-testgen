# ADR 0004 — Границы генерации и ограниченного self-repair

Статус: обновлено под ТЗ ARQA v3, п. 4.1.7.1 и MVP M3 (раздел 7.10).
Конвейер подключён к `build_agent` в режиме CLI `--generate`.

## Контекст

ADR 0002 закрепил, что runner только изолированно исполняет готовые pytest-тесты
и не вызывает LLM; ADR 0003 — что генератор сохраняет код версиями через
`prototype.storage`. ТЗ v3 требует ремонта конкретных ошибок синтаксиса,
импортов и фикстур. Падение проверки API и недоступность инфраструктуры сами
по себе не дают разрешения менять тест. Старое решение о ремонте URL/HTTP-методов
по падению assert заменено этим правилом.

## Решение

Вводится конвейер `run_generation_pipeline(GenerationSettings) -> GenerationRun`,
состоящий из шагов: генерация одного набора тестов по контракту (один
структурированный LLM-вызов) → детерминированная постобработка (`ast`, без
исполнения) → изолированный прогон через runner → **ограниченный** self-repair.
Для регистрации в агенте предусмотрен `create_generation_tool(settings)`:
адрес, сети, output-пути и лимиты задаёт доверенный оркестратор, аргументов
конфигурации от LLM нет. Старый `generate_tests_tool` остаётся адаптером только
для доверенных Python-вызовов. В `build_agent(generation_settings=...)`
регистрируется только инструмент с фиксированной конфигурацией; прежний режим
Schemathesis/user story сохраняется. Качество сценариев M2 проверяется отдельно.

### Что может исправлять self-repair

- Пропущенное двоеточие заголовка функции/класса восстанавливается обычным
  кодом для опорного AST; кандидат должен совпадать с ним по структуре.
- Допускается добавление `import pytest`/`import requests` и исправление
  известных опечаток импортов без затенения имён и изменения тела тестов.
- Диагностированные отсутствующие фикстуры `client`/`http_client`/`session`
  заменяются на `api_client`, `baseurl`/`api_url` — на `base_url` с согласованной
  заменой использований; коллизии и неоднозначные вложенные области отклоняются.
- **Файловый кандидат** — для ошибок синтаксиса, импорта и сбора: модуль целиком
  проходит структурный барьер. Неоднозначные ошибки требуют проверки человеком.
- **Функциональный ремонт** — для конкретных ошибок фикстур `test_*`-функций:
  из модуля через `ast` вырезается только упавшая функция (с декораторами),
  модель возвращает исправленную функцию, она подменяется в файле. Успешные
  тесты повторно не генерируются и не отправляются модели.

### Что никогда не вызывает LLM

1. `infrastructure_error`, `timeout`, `interrupted` — недоступность Docker/API,
   истечение лимита времени, прерывание. Ремонт не выполняется вообще.
2. Падение assert само по себе, в том числе документированный альтернативный
   статус → `suspected_defect`: тест не правится. Это повод проверить сервис
   и тест, а не доказательство дефекта сервиса и не разрешение подогнать ожидания.
3. Соединение/таймаут к адресу API при импорте или внутри тела теста — ошибка
   окружения, не повод для ремонта.

Правило «не ослаблять assert» проверяется кодом при применении ответа модели,
а также указано в промпте. Сохраняются assert, URL, HTTP-методы, данные запроса,
декораторы и структура исполнения. Неоднозначные преобразования отклоняются.
Ошибки подключения к API исключаются из ремонта при сборе, `error` и `failed`.

### Лимиты попыток и бюджета

- `max_repair_attempts` = 3 по умолчанию;
  переопределяется env `TESTGEN_MAX_REPAIR_ATTEMPTS`. Подсчитываются вызовы
  LLM на ремонт.
- Бюджет выходных токенов ремонта = 30 000, env
  `TESTGEN_REPAIR_TOKEN_BUDGET`; перед каждым вызовом проверяется
  `used_output >= budget`.
- Повтор одинаковой ошибки останавливает цикл: сигнатура ошибки — пара
  (цель «файл» / «файл::функция», нормализованная диагностика). Сигнатура
  нормализует пробелы, пути и номера строк, поэтому одинаковые ошибки
  сравниваются стабильно.

### Компактный пейлоад ремонта

В LLM отправляются только: фрагмент упавшей функции ≤ 30 строк, релевантный
фрагмент контракта (метод/путь/параметры/документированные ответы) ≤ 1500
символов и хвост диагностики ≤ 2000 символов.

### Версионирование попыток

Каждый запуск получает отдельный каталог `output_dir/<UTC-время>-<UUID>/`.
В нём находятся `attempt-N` и отчёты генерации; повторный запуск не подмешивает
старые файлы и не перезаписывает предыдущий отчёт.

Дубли имён файлов отклоняются до сохранения и запуска. Потеря части файлов
при постобработке не позволяет объявить генерацию успешной. Сбой сохранения
версии или отчёта даёт `infrastructure_error`, сохраняя факты выполнения.
Каждая попытка runner экспортирует JSON, Markdown и JUnit XML. При ошибке
финального ответа агента результат инструмента и отчёты M3 сохраняются;
CLI возвращает ненулевой код, не объявляя весь агентный цикл успешным.

Каждая попытка (генерация + каждый вызов ремонта) сохраняется отдельной
неизменяемой версией через существующий `save_test_suite(SaveRequest(…,
collect=False))`; `generator_meta` включает номер попытки. Сбор остаётся за
runner (ADR 0002/0003). Отступление от ADR 0003: runner запускается по каталогу
попытки конвейера, а не по `SavedSuite.tests_dir`, поскольку storage относит
файлы с синтаксической ошибкой в `rejected/` — а их ремонт должен видеть
precheck/collection runner.

## Последствия

- Успех каждой попытки проверяется новым прогоном runner; версия после
  неудачного ремонта тоже сохраняется (история для метрик).
- Консервативная классификация и AST-барьер могут отказать в ремонте исправимых
  ошибок. Кандидат, не прошедший барьер, не сохраняется и не исполняется;
  причина отражается в диагностике ремонта.
- Структурированный результат `GenerationRun` не содержит кода тестов; его
  читает tool/отчёт: `status`, `attempts`, `tokens`, `summary`, `repair_log`,
  `suspected_defects`, `environmental`, `saved_versions`.

Порядок проверки и ограничения: [проверка M3](../testing/m3-verification.md).
