# ADR 0004 — Границы генерации и ограниченного self-repair

Статус: принято; реализовано в `prototype.generator` (пп. 2.1.5 и 2.1.2 ТЗ).
Подключение к агенту (`build_agent`) — отдельным шагом, вне этого этапа.

## Контекст

ADR 0002 закрепил, что runner только изолированно исполняет готовые pytest-тесты
и не вызывает LLM; ADR 0003 — что генератор сохраняет код версиями через
`prototype.storage`. Пункт 2.1.5 ТЗ требует «реальной генерации» pytest-тестов
по контракту, а п. 2.1.2 — роста доли запускаемых тестов. Остаётся открытым
вопрос границ: в каких случаях сгенерированный код разрешено менять (и сколько
раз), а в каких — нет, чтобы тесты не превращались в подгонку под дефектный
сервис и чтобы расход LLM был ограничен.

## Решение

Вводится конвейер `run_generation_pipeline(GenerationSettings) -> GenerationRun`,
состоящий из шагов: генерация одного набора тестов по контракту (один
структурированный LLM-вызов) → детерминированная постобработка (`ast`, без
исполнения) → изолированный прогон через runner → **ограниченный** self-repair.
Программный API дополнен тонким tool `generate_tests_tool` для агента; копия
конвейера в агента не добавляется.

### Что может исправлять self-repair

- Ремонтируется только код, порождённый генерацией: синтаксис, импорты, пути и
  HTTP-методы, типы аргументов, выбор входных данных — при условии, что
  ожидаемый результат соответствует контракту.
- **Файловый ремонт** — для синтаксических/импортных/сборных ошибок
  (`collection_error`, `compatibility_issues`): модель возвращает исправленный
  модуль целиком.
- **Функциональный ремонт** — для упавших/ошибочных `test_*`-функций:
  из модуля через `ast` вырезается только упавшая функция (с декораторами),
  модель возвращает исправленную функцию, она подменяется в файле. Успешные
  тесты повторно не генерируются и не отправляются модели.

### Что никогда не вызывает LLM

1. `infrastructure_error`, `timeout`, `interrupted` — недоступность Docker/API,
   истечение лимита времени, прерывание. Ремонт не выполняется вообще.
2. Падение assert, при котором фактический статус противоречит
   документированным ответам контракта (например, получен 500, а в контракте
   его нет) → `suspected_defect`: тест **не** правится, assert **не**
   ослабляется. То же — если по коду теста нельзя сопоставить запрос операции
   контракта (консервативная классификация).
3. Соединение/таймаут конкретно к адресу тестируемого API внутри тела теста —
   не считается ошибкой кода и не ремонтируется.

Правило «не ослаблять assert» продублировано в системном промпте ремонта:
изменение ожидаемого статуса или структуры под фактический ответ — запрещено.

### Лимиты попыток и бюджета

- `max_repair_attempts` = 3 (значение из плана команды, `report_metrics.md`);
  переопределяется env `TESTGEN_MAX_REPAIR_ATTEMPTS`. Подсчитываются вызовы
  LLM на ремонт.
- Бюджет выходных токенов ремонта = 30 000, env
  `TESTGEN_REPAIR_TOKEN_BUDGET`; перед каждым вызовом проверяется
  `used_output >= budget`.
- Повтор одинаковой ошибки останавливает цикл: сигнатура ошибки — пара
  (цель «файл» / «файл::функция», нормализованная диагностика). Сигнатура
  нормализует пробелы, пути и номера строк, поэтому одинаковые ошибки
  сравниваются стабильно.

### Компактный пейлоад ремонта

В LLM отправляются только: фрагмент упавшей функции ≤ 30 строк, релевантный
фрагмент контракта (метод/путь/параметры/документированные ответы) ≤ 1500
символов и хвост диагностики ≤ 2000 символов.

### Версионирование попыток

Каждая попытка (генерация + каждый вызов ремонта) сохраняется отдельной
неизменяемой версией через существующий `save_test_suite(SaveRequest(…,
collect=False))`; `generator_meta` включает номер попытки. Сбор остаётся за
runner (ADR 0002/0003). Отступление от ADR 0003: runner запускается по каталогу
попытки конвейера, а не по `SavedSuite.tests_dir`, поскольку storage относит
файлы с синтаксической ошибкой в `rejected/` — а их ремонт должен видеть
precheck/collection runner.

## Последствия

- Успех каждой попытки проверяется новым прогоном runner; версия после
  неудачного ремонта тоже сохраняется (история для метрик).
- Консервативная классификация может отказать в ремонте исправимым ошибкам
  (например, опечатка в пути даёт `suspected_defect`), но гарантирует, что
  тест никогда не примет недокументированное поведение.
- Структурированный результат `GenerationRun` не содержит кода тестов; его
  читает tool/отчёт: `status`, `attempts`, `tokens`, `summary`, `repair_log`,
  `suspected_defects`, `environmental`, `saved_versions`.
